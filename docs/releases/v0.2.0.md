# v0.2.0 — Event Processing

## Release Summary

The v0.2.0 event-processing milestone transforms one supported Windows Event
XML record into a validated `NormalizedEvent`.

## What Is Included

- Typed raw and normalized event models with authentication, process, network,
  file, and DNS contexts.
- Windows Event XML ingestion and source-specific Windows Security and Sysmon
  normalization.
- An explicit parser registry and public XML-to-normalized-event pipeline.
- Seven synthetic, public-safe Windows/Sysmon fixtures, focused unit tests,
  and end-to-end integration and failure-path tests.
- [Event-processing architecture and examples](../architecture/event-processing.md).
- Consistent strict mypy backend import resolution across direct checks and
  pre-commit.

## Event-Processing Architecture

The public `normalize_windows_event_xml(xml)` entry point follows:

`Windows Event XML → RawWindowsEvent → parser registry → source normalizer → NormalizedEvent`

It ingests one XML record at a time. Registry dispatch is explicit; each source
normalizer validates its supported identity and builds a typed context. Named
source fields without a normalized equivalent remain in controlled `source_data`.
The pipeline does not invent absent optional values or return partial events.

Failures have a controlled boundary: `MalformedEventXmlError` for malformed
XML, `InvalidRawEventError` for invalid raw metadata, `UnsupportedEventError`
for unsupported identities, and `InvalidNormalizedEventError` for supported
events whose values cannot form a valid normalized context.

## Security and Safe Data

The committed fixtures are synthetic, using fictional/example hosts and
documentation IP ranges. They contain no production Windows/Sysmon telemetry,
SIEM/EDR exports, credentials, or personal information. See the
[safe-data policy](../../SECURITY.md).

## Current Limitations

v0.2.0 does **not** implement detection rules, a Detection Engine, runtime
detection matches, alert generation or management, analyst triage,
investigation workflows, IOC enrichment, MITRE ATT&CK runtime enrichment,
severity/priority decisions, escalation, persistence or a database, a backend
API/FastAPI service, or a web UI. It does not collect live telemetry, ingest
binary `.evtx`, or support arbitrary providers.
