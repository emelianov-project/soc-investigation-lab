# v0.4.0 — Alert Management

## Overview and output boundary

v0.4.0 is implemented and prepared for publication. Publication still requires
the `v0.4.0` tag and a published GitHub Release. The release adds a typed Alert,
explicit handling operations, and an in-process analyst queue on top of the
released v0.3.0 Detection Engine.

`DetectionMatch → Alert creation → Alert lifecycle / severity / priority → in-process queue`

The queue returns a `tuple[Alert, ...]`. Investigation begins beyond this
boundary. Alert Management takes an existing match with a TRUE root outcome
and preserves its evidence without rerunning detection.

The upstream pipeline still parses and normalizes one Windows Event XML record
at a time. Windows Security Events 4624, 4625, and 4688 and Sysmon Events 1, 3,
11, and 22 are the seven event identities inherited from v0.2.0. The six
declarative Windows and Sysmon rules were released in v0.3.0.

## Alert domain model, identity, and evidence

`Alert` is a frozen value with a caller-assigned `alert_id`, lifecycle state,
independent severity and priority, and three UTC timestamps. Its ID is a
lowercase ASCII slug of 1–128 characters with single hyphens between segments.
`created_at` stays fixed, and timestamps obey
`created_at <= state_changed_at <= updated_at`.

Each Alert owns a detached `source_match` snapshot. It retains the rule ID,
version and title, the typed normalized event, the TRUE root outcome, and the
complete ordered condition trace. Reading `source_match` returns a defensive
copy. Alert operations preserve the snapshot across creation, updates, and
queue reads without mutating caller-owned data.

## Public operations and deterministic creation

Import the operations and errors below from `app.alerts`. Import `Alert`,
`AlertState`, `AlertSeverity`, `AlertPriority`, and `DetectionMatch` from
`app.models`.

| Operation | Purpose |
| --- | --- |
| `create_alert(match, alert_id, created_at, *, severity, priority)` | Validate and snapshot a match as a new Alert. The keyword overrides are optional. |
| `acknowledge_alert(alert, at)` | Acknowledge a new Alert. |
| `close_alert(alert, at)` | Close an acknowledged Alert. |
| `set_severity(alert, value, changed_at)` | Set an active Alert's security significance. |
| `set_priority(alert, value, changed_at)` | Set an active Alert's handling urgency. |
| `list_alerts(alerts, *, states, severities, priorities)` | Validate and list Alerts with optional typed filters. |

`create_alert()` requires an explicit ID, a valid match, and a timezone-aware
`datetime`. It normalizes the supplied instant to UTC and initializes
`created_at`, `state_changed_at`, and `updated_at` to that instant. The defaults
are `NEW`, `UNASSIGNED`, and `NORMAL`. Creation uses no hidden clock or ID
generator and maintains no registration or deduplication state. Equivalent
inputs yield equivalent values.

## Lifecycle and timestamps

The lifecycle is `NEW → ACKNOWLEDGED → CLOSED`. Direct closure from `NEW` and
reopening a `CLOSED` Alert fail. `CLOSED` is terminal and records completion
of handling. Analyst verdicts remain outside the lifecycle.

Acknowledging an already acknowledged Alert and closing an already closed Alert
are idempotent. They still validate the Alert and the explicit timezone-aware
timestamp. A transition time must be at or after `updated_at` in UTC. Real
transitions return a validated value with new `state_changed_at` and `updated_at`
timestamps. No-ops retain the original timestamps.

## Severity and priority

Severity expresses assigned security significance. Values are `UNASSIGNED`,
`INFORMATIONAL`, `LOW`, `MEDIUM`, `HIGH`, and `CRITICAL`. Priority expresses
handling urgency. Values are `LOW`, `NORMAL`, `HIGH`, and `URGENT`.

Callers assign each value explicitly on `NEW` and `ACKNOWLEDGED` Alerts. A
change preserves the other policy value and the lifecycle state and advances only
`updated_at` to the supplied instant. A same-value assignment validates the
inputs and keeps the timestamps. Policy changes on `CLOSED` Alerts are rejected,
including same-value assignments. There is no automatic severity-to-priority
mapping, maliciousness classification, or verdict inference.

## In-process analyst queue

`list_alerts()` is a stateless read of a caller-supplied collection. It validates
the entire collection before filtering, rejects duplicate IDs even among filtered
entries, and returns an immutable tuple of detached Alert values.

The default state filter includes `NEW` and `ACKNOWLEDGED`. Callers can include
`CLOSED` explicitly. Omitted severity and priority filters are unrestricted.
Explicit filters must be nonempty sets or frozensets of the exact corresponding
enum type. Values are combined with OR within a filter and AND across filters.
An empty input or a valid filter with no matches returns `()`.

Results use this total order, independent of input enumeration:

1. Priority descending from `URGENT` to `LOW`.
2. Severity descending from `CRITICAL` to `UNASSIGNED`. `UNASSIGNED` ranks
   last within its priority group.
3. Oldest UTC `created_at` first.
4. ASCII `alert_id` ascending.

## Validation and controlled errors

| Error | Boundary |
| --- | --- |
| `AlertCreationError` | Invalid match evidence, ID, creation time, severity, or priority. |
| `AlertTransitionError` | Invalid Alert or time, backdated operation, or forbidden transition. |
| `AlertPolicyError` | Invalid Alert, policy value, or time, including a policy request on a closed Alert. |
| `AlertQueueError` | Invalid collection, Alert snapshot, typed filter, or duplicate ID. |

Shared validation rechecks Alert snapshots at operation boundaries. Failures
leave inputs intact and return no partial result. Public error diagnostics expose
a reason and, where applicable, a safe field name. They omit event and trace
contents and raw validation diagnostics.

## End-to-end coverage and quality gates

Offline unit tests cover the Alert model, creation, lifecycle, independent
policy changes, and the queue. XML-to-Alert integration covers all six existing
rules with synthetic Windows Security and Sysmon XML, complete evidence
preservation and isolation, and deterministic lifecycle and queue behavior.
Failure-path tests include malformed and unsupported XML, invalid and duplicate
rules, invalid matches or Alerts, forbidden operations, and diagnostic safety.
See [testing coverage](../testing.md#alert-management-coverage).

The release-preparation quality gate is:

```console
git diff --check
uv lock --check
uv sync --locked --group dev --group test
uv run --no-sync ruff check .
uv run --no-sync ruff format --check .
uv run --no-sync mypy backend/tests
uv run --no-sync mypy tests/integration
uv run --no-sync pytest
uv run --no-sync pre-commit run --all-files
```

The required PR check is `Backend quality` in the `Backend CI` workflow.

Local validation on Windows with Python 3.12 collected 1,442 tests.
**1,440 passed and 2 skipped.** The existing file and directory symlink tests
were skipped because the OS did not permit symlink creation. The deterministic
link and path-containment tests still ran and passed. These counts are from the
local pytest run.

## Security and safe data

The tracked-content review applied the [security policy](../../SECURITY.md) to
repository configuration, backend and test code, detection rules, XML fixtures,
documentation, and release notes. It screened for credential patterns and
sensitive file types and reviewed example hosts, addresses, accounts, paths,
and fixture provenance. The review found synthetic XML and rule data, reserved
documentation addresses, fictional lab accounts and paths, and a comment-only
environment template. It identified no committed secrets, private keys,
production telemetry, personal or customer data, or suspicious binaries in
the reviewed snapshot.

The review was limited to tracked content. Real match evidence may contain
sensitive event or trace values. Apply the security policy before logging or
exporting evidence.

## Current limitations and next milestone

The queue is in memory for the duration of a call. v0.4.0 does not include:

- Investigation, evidence collection workflows, analyst notes, timelines,
  related-event discovery, True Positive or False Positive verdicts, or escalation.
- Automatic Alert scoring or triage, IOC or MITRE ATT&CK runtime enrichment,
  or cross-event and time-window detection correlation.
- Persistent Alert storage, databases, ORM or migrations, an HTTP API,
  authentication or authorization, or a web UI.
- Notification delivery, streaming, or live telemetry collection.

v0.5.0 — Investigation Workflow is the next planned milestone.
